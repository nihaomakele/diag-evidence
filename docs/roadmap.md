# DiagEvidence 后续三阶段路线

0.1.1先以修正后的研究预览发布。下面各阶段按可验收成果推进，不将未来能力提前写入README。

## 第一阶段：做成别人能复跑的一套真实流程

目标：让用户接入一个真实振动分类服务和一个来源明确的检索库，完成信号→工具输出→核验→受限报告→轨迹回放。

交付：一套来源/权限明确的数据清单、独立原始记录/设备划分、固定预处理和模型revision、真实HTTP端到端示例、一条完整追溯链。训练/调参只使用训练/验证部分，先分设备或原始记录再切窗；保留模型实际错误，不能只挑正确案例。

验收：新使用者按文档在独立环境复跑；相同输入可对应相同冻结工具输出；准确列出真实与替身组件。报告真实分类错误、工具失败及核验结果，而非仅报告演示跑通。当前三故障类别没有健康/未知类，补数据和策略前不把其最高分解释成“设备一定有故障”。

## 第二阶段：证明核验层带来了什么

目标：判断身份和时间适用性规则是否能减少错误的高强度结论，同时保留合理输出覆盖。

交付：冻结同一批上游预测/检索结果，建立格式合法但语义不适用的故障基准：设备错配、来源同号、同一record的多chunk/改写、采样率/单位错配、窗口错配、过期证据、在决策时尚不可获得的未来证据；每类都有正常近邻对照与预先定义的期望语义。引入 `asset_id/channel/units/sampling_rate/window/as_of/available_at/preprocessing_revision/model_revision/record_id/source_id` 的适用协议，明确unknown规则。

对照：直接输出、严格schema/范围校验、简单confidence阈值、当前规则、新适用性规则；另在通用validator中装载相同规则作为实现控制。消融身份、时间、去重与unknown门控，避免把不同上游模型的效果误算为核验层收益。

验收：同时报告强结论中错误率、全部样本中强错误比例、覆盖率、正常误拒、故障检出/漏检、延迟和成本；无强结论时条件错误率记N/A。按设备/原始记录估计不确定性，不能把相邻窗口当作独立样本。若通用框架装载相同规则效果相同，应报告封装与可移植性价值，不能宣称框架选择就是新算法。

## 第三阶段：围绕无人系统验证决策价值

目标：把核验层用于无人系统中多个信息源/智能体的协同决策边界，选择一个具体任务，而非给当前固定流程更换“多智能体”名称。

建议先选受控仿真中的协同巡检或多机器人任务分配：各智能体提交带身份、观测时刻、可用时刻、坐标/单位和来源的结构化证据；决策层明确哪些证据可用于当前任务。先保留集中式或已知调度基线，再研究信息异步、过期、来源重复、通信丢包/延迟和观测冲突下的门控。

交付：任务/通信/观测模型、agent数量与职责、可复现仿真场景、集中式/无核验/有核验/消融基线。只有实际存在多个独立观测/行动主体及相互影响，才讨论多智能体协同决策。

验收：任务成功率、完成时间、通信/计算成本、违规或失效次数，以及拒绝/等待造成的机会成本。若方法没有提升任务效用，则不能仅凭证据检查命中率称“协同更好”。TimesFM仅在有明确预测目标和时间协议时作为独立上游预测实验；其预测误差不自动等于故障识别或协同决策收益。

这条路线的顺序是：真实工作流可复跑 → 同一上游条件下证明核验收益 → 在明确无人系统任务中证明决策效用。第一阶段是实用开源工具建设，第二阶段才开始形成可检验研究问题，第三阶段才与导师的无人系统多智能体方向建立实质联系。
