# 项目讲解与面试准备

## 一句话介绍

“这是一个多机器人协同巡检调度原型。我把消息核验放进在线派工循环，通过路径规划、任务分配、故障重派和回放，观察信息错误怎样影响任务执行。”

## 三分钟演示顺序

1. 运行`diag-evidence patrol-demo --scenario mixed --seed 7`，打开输出的回放HTML。
2. 在时刻0比较三张地图：任务与机器人相同，旧完工消息和相反观测使候选任务集合发生变化，计划路径已经不同。
3. 点击“下一条异常”，查看转发去重、身份冲突，以及机器人临时故障。暂停后指出哪个任务被取消、释放或重新派给其他机器人。
4. 拖到末尾，比较按时完成、移动、能量和重复复检。默认示例为4/8与8/8；再展示批量实验，而非仅展示这个示例。
5. 用报告延迟场景解释下一步：完工确认晚到会造成重复复检，应完善确认和幂等机制。

回放中填色为环境实际状态，虚线圈为调度器判断。两者分开，便于解释“为什么当时会这样派工”。

## 常见追问

**核验究竟改变了什么？**

它更新任务的“待办/完成/冲突”判断，从而改变候选任务集合和分配矩阵。在同一时刻、相同机器人状态下，分配器因此可能派给不同机器人或触发复检。

**为什么既有贪心又有精确匹配？**

贪心便于理解且开销低。匹配DP可以发现贪心先占一条高收益边、导致另一机器人失去好任务的情况。项目用小矩阵穷举检查DP结果。

**精确匹配优化的是什么？**

当前时刻的总派工收益，包含任务优先级、路径和服务代价。整个任务过程中还会出现新任务、交通等待和消息变化，因此继续按时间步重新决策。

**真实状态参照为什么偶尔低于延迟策略？**

信息改变派工顺序和后续路径，而当前算法优化单步收益。该参照用来分析信息条件，其完整任务完成率也由同一个闭环测量。

**怎样验证执行安全？**

每一步检查单元格互斥、迎面交换、合法移动和能量非负，测试另从轨迹核对这些约束。故障与恢复会改变可用机器人集合。

**集中式还是分布式？**

首版使用集中式调度器和多个独立执行实体。后续分布式扩展需要加入局部任务视图、协商消息和分配一致性机制。

**为什么重复消息去重以后，延迟场景仍有很多复检？**

消息去重处理信息身份；任务执行幂等处理动作是否应再次执行。当前完工报告晚到时，调度器可能再次派发复检。下一阶段将设计任务确认与在途租约，分别测量等待成本和重复执行成本。

## 可以据实整理的项目经历

在理解并能演示上述代码后，可据个人实际参与情况整理为：

“开发并维护多机器人协同巡检调度原型，集成A*、精确单步匹配和决策前信息核验；构建8类扰动与离线交互回放，完成1920次配对仿真。项目整体340项回归通过，其中32项为新增调度检查；在预留布局的混合扰动中记录到49.375%与99.375%的按时任务完成率，并定位报告延迟导致的重复复检问题。”

面试中说明自己的设计、实现、复现和修改部分，并展示一次亲自完成的扩展。建议先独立加入“任务执行确认/幂等”功能，保留改动前后实验及代码差异，形成可解释的个人贡献。

## 后续成长顺序

1. 执行确认、租约、取消和重试，补齐任务生命周期。
2. 将机器人状态、导航动作、执行结果映射到ROS2适配接口。
3. 保留集中式基线，再研究拍卖或其他分布式分配。

这条路线能持续积累算法、状态机、接口、测试和实验设计经验，并逐步贴近无人系统协同决策。
